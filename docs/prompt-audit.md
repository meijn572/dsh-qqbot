## 0. 这份文档要解决什么

现在的提示词里，硬规则太多、范例太少。

问题不在“管得严”，在：

```text
规则很难覆盖所有情况
规则容易让它死板
规则让它不敢发挥
```

宽松的说明 + 几个恰当的范例，效果更好。

这份文档先汇总现状，再一项一项敲定怎么改。

## 1. 判断标准

改的时候看三条。

```text
1. 这条规则能不能换成一句说明 + 一个例子
2. 这条规则是不是在管“形式”（字数、条数、长度）
3. 这条规则是不是只写了「不要」，没写「要什么」
```

形式类的阈值最该退。

真正需要留的：

```text
事实边界（不能编、不能换主语）
输出格式（JSON 结构、字段名）
真正的禁止项（隐私、外发）
```

## 4. 通用改法

不是每条都套同一个模板。大致三种情况。

### 4.1 形式阈值 → 说明 + 例子

```text
改前：
  4–10 条短句，总长 120–500 字。

改后：
  写成几条短句，看有多少真变化就写几条，别为了凑数。
  像这样：
  - 说话简洁，结论先说。
  - 他难受的时候先停一下，不急着给方案。
```

### 4.2 禁令 → 正例

```text
改前：
  不写主人、私聊、群、token、记忆系统；不写广告/引流/敏感内容。

改后：
  说说只写你自己看到、想到的东西，别人看了也看得懂。
  像这样：
  - 楼下新开那家店的招牌灯坏了半边，晚上还是一样亮。
  - 今天把一段代码删了又加回来，来回三遍。
  私事、聊天记录、工作细节都不往外说。
```

### 4.3 比喻 → 实例

```text
改前：
  标准：只有被戳到、心里确实起了波动才记。

改后：
  回想这段对话，有没有哪一句让你停下来，或者当时就想回一句多余的。
  像这样：
  - 他说「我答不上来，但告诉自己那是变聪明的我」——这句我记住了。
  - 他连着骂了三句，我没什么感觉，不记。
```

## 5. 需要留的规则

不是所有规则都要松。这几类建议保留：

```text
事实边界：不能编、不能换主语（L1/L3 已有）
输出格式：JSON 字段名和结构
真正的隐私边界：私聊不外传
```

理由：这些不是“管形式”，是防止出错。
