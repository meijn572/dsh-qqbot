# 架构整理计划

写于 2026-11-15。这是**执行计划**，不是目标形态。
目标形态见 [architecture-three-tiers.md](architecture-three-tiers.md)。

---

## 一、为什么是整理，不是重写

先看规模：

```text
后端 service    30 文件  10859 行
桥接 qqbot      38 文件   3346 行
bridge.py        1 文件   2811 行
合计                    17016 行

测试            17 文件    836 行
```

17000 行不是重写的主要障碍。真正带不走的是**三个月踩出来的具体经验**：

```text
DeepSeek 的 system 更新必须夹在 user 之后，插在 assistant 后面会让整条会话永久报错
会话投影偶尔读不出来（01:17 那次），重试 3 次再判损坏才有意义
B 站选材会自我强化，得靠「别从最近看的里找题目」这句约束
L3 的 open 状态会被默认值污染，一次冒进就攒了 19 条
人格一变就必须换会话，否则每轮都撞同一条错
```

重写的话，这些坑要重新踩一遍。

**但"搬来搬去"也不对**——搬完代码总量不减少，只是位置变了。
真正的病灶是**边界不清楚**：

```text
桥接    知道太多业务（该注入什么、怎么拼、什么时候跑）
插件    知道太多业务（app.mjs 1030 行）
后端    只做存储和提炼，不知道"复盘"这件事
```

所以这份计划的目标是**划清边界**，不是"把东西挪个地方"。

## 二、四个阶段

顺序不能换。每一步都依赖前一步的产出。

```text
阶段一  定契约          不动代码，写接口清单和归属规则
阶段二  后端补产能      纯增量：多轮会话 + 任务执行入口
阶段三  逐个迁复盘      一次一个，profile → style → important → review
阶段四  清理           插件瘦身、桥接拆分
```

### 为什么这个顺序

```text
插件瘦身不能先做   后端还没有 /input/<recipe>，插件只能继续自己拼
复盘迁移不能先做   后端没有多轮会话，搬过去会贵 4-5 倍
清理不能先做       前面没完成就整理，等于整理两遍
```

---

## 三、阶段一：定契约

**目标：每一步后续工作都有依据。**

产出两份东西：接口清单、归属规则。

### 验收标准

```text
每条接口都写清楚：谁调、传什么、返回什么、失败什么样
每个模块都写清楚：它该做什么、不该做什么
看完这份文档，能判断"某段代码该放哪"而不需要问我
```

### 这一阶段不动代码

---

## 四、阶段二：后端补产能

**目标：后端有资格接复盘。**

现在后端缺两样：

```text
一、LLM 只能一问一答         llm.chat(system, user)，硬编码两条消息
二、没有任务执行入口         /input/<recipe> 只给素材，不调模型
```

补四件事：

```text
1. llm.chat_messages(messages)      带历史的多轮调用
2. task_session 表                   每个任务的会话持久化
3. 会话管理器                        加载 / 追加 / 轮换 / 裁剪
4. POST /task/<name>                执行器
```

### 为什么用数据库表存会话

```text
后端已经有 SQLite，不用新开目录
会话更新和落库能一起提交
以后要查「某任务历史上说过什么」直接 SQL
```

### 验收标准

```text
/task/profile 能跑通
连跑两次，第二次日志里能看到缓存命中（DeepSeek 返回 prompt_cache_hit_tokens）
```

### 这一阶段不碰任何现有逻辑

现有的四个复盘继续在桥接侧跑，不受影响。

---

## 五、阶段三：逐个迁复盘

**目标：四个复盘全在后端，桥接只剩调度。**

顺序按复杂度：

```text
一、profile    最简单：取素材 → 调模型 → 写 persona
二、style      加一步：改人格「表现」节
三、important  加一步：改人格「重要的事」节
四、review     最复杂：产出提案，等人确认
```

### 每个迁完跑一周

**一次只迁一个。** 出问题是哪一个，一眼能看出。

### 验收标准

```text
迁移前后产出质量不降（对比几次真实产出）
桥接对应的 *_loop 已删
服务端 scheduler 接管触发
```

---

## 六、阶段四：清理

**目标：插件和桥接变薄。**

```text
插件   app.mjs 的业务判断下沉到 /input/<recipe>
       表情本地匹配下沉到 /meme/search
       内联提示词合并到 qqbot/domains/prompts.py

桥接   bridge.py 拆成 msg.py（收发）/ router.py（去重合并）/ extras.py（附加信息）
```

### 验收标准

```text
插件 < 800 行（现在 6125，其中 client.js 3939 是浏览器资产不能动）
bridge.py < 1500 行（现在 2811）
```

## 七、风险

### 一、缓存的依赖是"前缀一字不差"

```text
system 段      必须固定，人格不能每轮变
历史消息       只会往后追加，不能修改
素材           每次追加在末尾
```

**搬家过程中如果改了提示词，缓存全部失效**，成本优势就没了。
所以阶段三每迁一个，提示词要定下来再跑。

### 二、会话超长会报错

```text
DSH 那边是 30k token 换新会话
后端要一样，否则超过模型上下文上限直接报错
```

### 三、并发

```text
DSH 有 MAINT_LOCK 防并发
后端要加锁，避免两个任务同时跑同一个会话
```

### 四、迁移期间两套并存

```text
迁了一个之后，它走后端；没迁的还在桥接
两套调度同时在跑，要确认不会重复触发
```

## 八、每个阶段的完成标志

| 阶段 | 完成标志 |
| --- | --- |
| 一 | 有契约文档，每条接口写明调用方和返回结构 |
| 二 | `/task/profile` 跑通，第二次调用日志里有缓存命中 |
| 三 | 四个复盘全在后端，桥接只剩调度，产出质量不降 |
| 四 | 插件 < 800 行，bridge.py < 1500 行 |

## 九、阶段二之后要停一段

阶段二改的是基础设施。做完之后**不要立刻进阶段三**，先让现有的四个复盘在旧路径上继续跑一周：

```text
确认新基础设施不影响他们
确认缓存确实生效
确认没有内存泄漏（长跑的任务会话）
```

**这一步不能省。** 基础设施出问题，后面全白干。

---

## 十、什么时候才该重写

如果以后真到了要重写的地步，触发条件应该是：

```text
一、某模块修改成本持续高（每次改动都踩坑）
二、数据模型要大改（L2 彻底删、L3 拆结构）
三、换技术栈
```

现在三条都不成立。**所以是整理，不是重写。**
