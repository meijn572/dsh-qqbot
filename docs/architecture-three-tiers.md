# 三块架构

写于 2026-11-15。这份文档说「东西该在哪」，不描述现状。
现状见 `architecture-current.md`。

---

## 一、为什么分三块

不是按功能分，是**按独占资源分**。

```text
后端服务    独占 SQLite
插件        独占 DSH 引擎的注入点
桥接        独占 OneBot 连接
```

三块之间只有 HTTP。任何一块挂了，另外两块的数据不会坏。

看两个反例就明白这个标准怎么用：

**反例一：把复盘搬到后端**

```text
表面理由    复盘只读记忆、调模型、写记忆，很像后端的事
实际问题    后端每次全新调用，没有会话前缀缓存
实测对比    DSH 会话缓存命中 90%+（maint-sticker 283k 命中 / 18k 新增）
            后端 0% 命中
成本        同样的输入，后端贵 4-5 倍
```

复盘低频、输入长，正需要缓存。**它该留在有会话的地方。**

**反例二：把人格注入交给桥接**

```text
表面理由    桥接本来就在拼 bridge-note，多拼一段人格也不麻烦
实际问题    人格放进 user 消息 → 每轮都变 → DSH 的缓存前缀失效
            人格放进 system 段 → 稳定前缀 → 缓存命中
```

插件存在的唯一理由就是这个：**它能改 system，桥接不能。**

## 二、三块各自做什么

### 后端服务（一个进程）

**管数据，管思考，不管说话。**

```text
存储        SQLite：L0/L1/L2/L3/L4、日记、人格、词库、表情索引
取数        inputs.py：按取法取行（rows / search / batches）
渲染        render.py：把行变成给人看 / 给模型看的文本
提炼        extractor.py：所有 LLM 提炼任务
                 L0→L1 批量、L1 压缩、L2 推断、L3 事件、L4 挑选
                 日记、去重判断、睡前整理
接口        /input/<recipe>      取素材（不调模型）
            /ingest /search        写入与检索
            /persona /state /diary 读接口的薄包装
```

**判断标准：这个任务需不需要跨次记忆？**

```text
不需要  →  后端（提炼管线，每 5 分钟一批，无历史依赖）
需要    →  DSH 会话（复盘要靠上次输出，或者靠缓存省钱）
```

### 插件（薄）

**只做一件事：连接 DSH 的注入点。**

```text
index.mjs            注册
hooks/persona.mjs    取 /persona 的 text，包一层 <dsh-remembers source="persona">
hooks/state.mjs      取 /state 的 render，包一层 XML
hooks/recall.mjs     转发 /input/recall
hooks/turn_end.mjs   转发
tools/*.mjs          每个工具 10-30 行：解析参数 → 调后端 → 返回
client.js            浏览器设置页（React），只能在这
```

**不该有的**：业务判断、提示词、本地匹配逻辑、状态机。

判断标准：**删掉这一行，DSH 会不会少一个能力？**

```text
会   →  留着（注入点、工具注册）
不会 →  挪走后端
```

### 桥接（薄）

**只做一件事：搬运 QQ 消息。**

```text
收消息      去重、合并、决定要不要回
发消息      气泡切分、表情、图片
拼附加信息  群里学到的说法、她自己留着没问的话、不回规则
调度        什么时候跟 DSH 说一句话（B站、主动说、复盘）
```

**不该有的**：写提示词、做业务判断、直接读写 SQLite。

## 三、现在错位的部分

```text
插件 app.mjs          1030 行，混了业务编排
插件 tools/memes.mjs   217 行，本地做表情匹配
桥接 qqbot/domains/    8 处内联提示词，各写各的通用规则
桥接 bridge.py        2700 行，收发 + 调度 + 拼装混在一起
```

### 插件里该挪走的

```text
业务编排  app.mjs          判断该注入什么、怎么拼 → 后端出 /input/<recipe>
本地匹配  tools/memes.mjs   表情匹配 → 后端出 /meme/search
```

### 桥接里可以吸收的

```text
内联提示词  8 处   加一个 qqbot/domains/prompts.py 放通用规则
                   或者从后端拉一次缓存（/prompts/common）
```

### 不该动的

```text
桥接的调度逻辑    B站几点刷、复盘几天一次——这是"什么时候跟 DSH 说话"，
                 属于桥接的职责
```

## 四、通用规则的归属

规则分三类，各有各的家：

```text
跨进程共用    称呼约定（「我：」是你，「主人：」是九歌）
              只写真实的、只返回 JSON
              → 后端出 /prompts/common，桥接启动时拉一次缓存

后端内部共用  VOICE_RULE / FAITHFUL_RULE / JSON_RULE
              → service/prompts.py

来源分层说明  L0 是什么、L2 能怎么用
              → 在渲染层（_ref_label），跟着每条来源走
              → 不在提示词里重复写
```

最后一条是这轮刚做的：把「L2 是判断，引用时要写我猜」从提示词挪到来源标签上，
每条来源自带用法说明，提示词里那段删掉。

## 五、拆分标准

想拆一个新的服务之前，问三个问题：

**一、它独占什么资源？**

```text
独占   →  可以独立
共享   →  不该拆（共享库 = 隐式耦合，拆了进程还是要联表）
```

比如人格条目的 `source_ids` 指向 L3，这两个概念看起来是两回事，
但必须在同一个库里做关联。**不能拆。**

**二、它的负载特征跟别人差多少？**

```text
差很多  →  值得拆（B站抓取要联网、会失败重试；记忆服务几乎零 QPS）
差不多  →  不值得（多一次 HTTP，多一处失败点）
```

**三、拆了之后调用链变多长？**

```text
一次日记要：取素材 → 调模型 → 落库
拆成三个服务 = 三次 HTTP + 部分失败处理
现在数据 30k 字，QPS 接近零，拆了收益看不出来
```

**结论**：后端保持一个进程，内部按模块分文件。不拆进程。

## 六、目标形态

```text
┌──────────────────────────────────────────────┐
│ QQ / OneBot                                   │
└──────────────────────────────────────────────┘
                    ↕
┌──────────────────────────────────────────────┐
│ 桥接 bridge.py                                │
│   收 → 去重合并 → 决定回不回 → 交给 DSH        │
│   拼附加：黑话 / ask_him / 不回规则             │
│   调度：B站 / 主动说 / 复盘（需要 DSH 会话的）    │
└──────────────────────────────────────────────┘
                    ↕
┌──────────────────────────────────────────────┐
│ DSH 会话                                      │
│   人格 / 状态注入（插件）                       │
│   工具调用（插件注册）                          │
│   复盘：靠会话缓存，输入长也不贵                 │
└──────────────────────────────────────────────┘
                    ↕
┌──────────────────────────────────────────────┐
│ 后端服务                                      │
│   memory_core   存储                          │
│   inputs        取数配方                       │
│   render        排版                          │
│   extractor     所有 LLM 提炼                  │
│   prompts       提示词常量                     │
└──────────────────────────────────────────────┘
```

## 七、落地顺序

按风险从低到高：

```text
一、提示词集中
    后端建 service/prompts.py，合并 VOICE_RULE / FAITHFUL_RULE / JSON_RULE
    桥接建 qqbot/domains/prompts.py，8 处内联改成引用
    风险低：只改常量，不改逻辑

二、插件瘦身
    app.mjs 里的业务判断下沉到 /input/<recipe>
    tools/memes.mjs 的匹配逻辑下沉到 /meme/search
    风险中：插件改动要重启 DSH 才生效

三、桥接瘦身
    bridge.py 拆成 msg.py（收发）/ router.py（去重合并）/ extras.py（附加信息）
    风险中：动的是主链路

四、复盘迁移
    这一步暂时不做。理由见第一节反例：DSH 会话有缓存，搬走会贵 4-5 倍
    除非以后发现"跨次记忆"反而成了负担
```
